# PDA v2 架构设计

> 本文规定项目级边界。遇到未覆盖且会改变依赖方向、数据归属或持久化语义的设计，先提出方案并与 Operator 确认；功能内部的局部决策记录在对应功能文档中。

本架构设计的五个原则：
* 按职责分层，不为本地存储增加空转接口
* 模块内部，层次单向依赖，数据单向流动
* 模块间不直接依赖
* 分层数据校验
* 设计保持空间，实现保持简洁

## 1. 组织方式

按功能组织代码，不强制按层建立文件夹。用文件后缀标记主要职责：`*.model.dart` 表示领域模型与规则，`*.case.dart` 表示用例与业务编排，`*.store.dart` 表示本地存储，`*.widget.dart` 表示页面与界面组件。文件较多时按功能内的实际关联分子目录；表声明、映射和跨功能 port 等辅助文件按职责命名，不强行套用四种后缀。模块边界由公开入口和导入检查约束，不由目录层数决定。

```text
lib/
  core/                 # 与 feature 无关的公共模型、接口、界面和设施
  features/
    ids/
    academic_course/
    custom_course/
    physics_experiment/
    other_experiment/
    timetable/
      timetable.model.dart
      timetable.case.dart
      timetable.store.dart
      timetable.widget.dart
      ...                # 文件多时按实际关联继续分组
  integration/
    dispatcher/         # 实现消费方接口，委派给其他功能
    database/           # 组合共享数据库结构与连接实现
    setup/              # 启动装配与应用生命周期
  main.dart             # 应用入口
```

示例后缀表示职责，**不要求每个功能都有四种文件**。`core` 同样按需要组织公共值对象、接口与界面，例如接收页面参数的 `AppShell`；这些代码不引用 feature。具体页面由启动装配传入。共享设施若需要功能配置，由启动装配注册。

## 2. 模块归属与接线位置

按规则和数据的归属划分一个模块是属于 `core` 还是 `features`。

| 类型 | 归属标准 | 示例 |
| --- | --- | --- |
| 无状态核心基础件 | 提供不依赖具体业务的公共接口、值对象或纯规则 | 公共值对象、通用格式转换 |
| 有状态核心基础件 | 持有应用级的通用状态或设施，不决定某项业务逻辑的规则 | 偏好存储、全局主题状态 |
| 功能模块 | 拥有明确的业务规则、数据或用例，可以有状态，也可以无状态 | 课程、实验成绩等 |

确定归属时，先找出规则由谁定义，再确定实例的生命周期和消费者所需的接口。某项业务数据即使被首页、提醒和原生 Widget 共用，仍由其功能模块维护。消费者不能因为复用范围广就把它移入 `core`。**`core` 不导入功能模块，也不包含功能专属模型或规则。**

`integration/dispatcher/` 实现消费方声明的跨功能 port，委派给提供方。`integration/database/` 组合共享数据库结构与连接实现，不接管功能专属的表、映射和读写规则。`integration/setup/` 创建对象、注入依赖、组装页面并管理应用或账号生命周期。三者都不取得业务数据的所有权。双方使用同一公共接口时，启动装配可以直接接线。`main.dart` 保留应用入口，将启动装配交给 `integration/setup/`。

界面使用 `provider` 取得启动装配或功能入口注册的依赖，避免在 Widget 构造参数中逐层传递；不要求依赖都另建接口。状态仍由所属模块持有，使用 signal 的状态由 signal 驱动响应式更新。只有 `core` 中的功能可以通过 Provider 全局注入依赖，其他的普通 Feature 不应该将功能泄露到全局的空间内。

## 3. 依赖方向

| 层次 | 依赖的层次 | 说明 | 外部依赖 |
| --- | --- | --- | --- |
| `core` | 无功能模块 | 放与 feature 无关的公共模型、接口、界面和通用设施 | 模型与业务接口仅依赖 Dart；面向界面的只读状态接口可依赖 signals；界面可依赖 Flutter，设施可依赖数据库等外部库 |
| 领域模型（`*.model.dart`） | 按需依赖 `core` 的公共值对象 | 定义本功能的模型、规则和自身校验 | Dart 语言原生类型 |
| 网络接口（`pda_repository`） | 不依赖功能模块或具体网络实现 | 定义纯 Dart 的远端能力接口及必要的交互类型，由 `pda_network` 实现 | Dart 语言原生类型 |
| 跨功能 (`*.port.dart`) | 本功能的领域模型，按需依赖 `core` | 由消费方声明需要其他功能提供的最小能力，不暴露提供方的专属模型 | Dart 语言原生类型 |
| 用例（`*.case.dart`） | 本功能的模型、按需使用本功能的 store、注入的数据库能力、跨功能 port、`pda_repository` 及 `core` | 编排业务操作；本地读写可直接使用数据库能力，不要求逐层转发的接口 | 按需使用数据库查询能力，不直接依赖功能专属平台插件或网络实现 |
| 本地存储（`*.store.dart`，按需设置） | 本功能的模型、按需依赖 `core` 和注入的数据库能力 | 集中需要复用或保持原子性的本地读写与映射；不要求同形的持久化接口 | 数据库、安全存储等外部库 |
| 界面（`*.widget.dart`） | 本功能的用例、模型，按需依赖 `core` 和纯 Dart 交互类型 | 管理界面交互状态，共享业务数据由所属功能提供，页面不各存一份真值 | Flutter、状态管理库 |
| `integration/dispatcher` | `core`、提供方的公开入口及消费方的 `ports` | 实现消费方的跨模块接口，委派给提供方；语义不同时在接口实现中适配 | 不为外部包单设转发层 |
| `integration/database` | `core` 及各功能公开的表声明 | 组合共享数据库结构与连接实现；不包含功能专属读写规则 | 数据库库及连接设施 |
| `integration/setup` | `core`、`integration/dispatcher`、`integration/database` 及各功能的公开入口 | 创建对象、注册共享设施、接线、组装页面、注入并管理应用或账号生命周期 | 必要的外部实现或平台插件 |
| `main.dart` | `integration/setup` 及入口所需设施 | 初始化 Flutter 和应用级错误处理，并启动应用 | 入口所需的平台或框架能力 |

功能模块之间禁止直接 import 或 export，包括对方的公开入口。消费方在自己的 ports 声明所需能力；`integration/dispatcher/` 实现该接口，并通过提供方的公开入口委派。`integration/setup/` 将接口实现注入消费方；双方已使用同一公共接口时直接接线。接口实现按消费端组织在 `integration/dispatcher/` 下。

领域模型与跨功能 port 按需使用 `core` 的纯 Dart 公共值对象；界面还可使用公共界面和只读响应式状态接口。用例可使用注入的数据库能力或本功能的具体 store，本地持久化**不强制接口反转**。共享连接由启动装配创建并管理生命周期，功能专属的表、映射和读写规则仍归该功能。导入检查覆盖 import 和 export，并检查网络实现没有经公开入口进入用例。

外部包按职责接入：界面组件由界面使用，网络实现放在 `pda_network` 并通过 `pda_repository` 的接口注入，本地存储实现可由本功能直接持有，应用级插件由启动装配管理。需要跨功能能力时使用消费方 port 和 `integration/dispatcher/`。领域模型、跨功能 port 和用例不直接依赖功能专属平台插件。

## 4. 分层分粒度数据校验

校验按所需信息放在能作出判断的最内层。外部数据进入系统时解析一次，内部传递已验证的类型，不在各层重复猜测数据是否合法。

领域模型借用 SSA 的单次赋值思想：构造后不可修改字段，也不通过可变集合间接修改。状态变化创建新的模型，并重新经过构造校验；模型不提供 setter 或原地修改方法。

| 位置 | 校验粒度 | 失败处理 |
| --- | --- | --- |
| 外部数据的解析与映射 | 网络实现或本功能的存储代码检查响应、数据库记录或导入文件的格式、必需字段及类型，再构造领域对象；映射代码不决定业务规则 | 损坏或无法表示的数据明确报错，不伪造默认值或空结果 |
| `domain` 与 `core` 的值对象 | 在构造时保证对象自身的不变量，例如起止时间有序、周次集合非空；不查询外部状态 | 拒绝构造非法对象 |
| 实际执行本地写入的用例或 store | 检查依赖当前持久化状态的规则，例如关联对象是否存在；由实际写入方保证校验与写入的一致性，本地数据库使用同一事务 | 需要原子性的操作不得部分提交；远端能力由接口定义和服务端实现保证 |
| 数据库约束 | 兜底保证非空、唯一性、外键和适合由数据库表达的基本范围；复杂结构由映射和领域对象继续校验 | 拒绝非法写入，不代替领域校验 |
| `application` | 检查跨操作的流程前提和转换能否成立；不重复持久化状态校验 | 阻止后续操作并报告可处理的失败 |
| `integration` | 对跨模块适配后的结果检查消费方接口要求；双方共用同一公共接口时不重复校验提供方模型 | 保留接口约定的结果状态，不将失败伪装成成功 |
| `presentation` | 校验表单输入并反馈字段错误；提交后展示用例返回的失败，不自行判断依赖数据库状态的规则 | 保留用户输入，允许修正或重试 |

需要稳定引用的派生数据，由所属功能定义可重复的 ID 生成规则，并验证同一输入得到同一 ID、不同实体不会冲突；这不能只靠单个对象的构造校验。

## 5. 数据与运行时要求

- **数据归属：** 每类业务数据明确权威来源和所属功能。远端数据、本地缓存与界面状态各有用途；写入和失效规则由所属功能定义。相同上下文和生命周期的消费者复用只读查询、订阅或快照，不各自维护可写真值。页面与外部服务共用业务快照时，由所属功能的 application 公开只读查询或订阅，启动装配按账号或应用生命周期创建和释放共享读取。首次读取不依赖页面打开。presentation 持有筛选、表单草稿等交互状态。派生数据由所属功能生成；是否缓存或持久化由实际需求和测量决定。
- **快照更新：** 有持久化缓存的功能先提供缓存快照，再独立于页面发起刷新；订阅时立即发送当前快照，之后只在对外结果变化时通知。新结果校验并持久化成功后才替换快照，刷新失败保留旧数据。对外只暴露消费者需要的只读数据、上下文与版本，不暴露内部可写状态或网络过程；跨功能由消费方接口和 `integration/dispatcher` 接线。响应式数据基于 Signals 实现，而不是 Stream。
- **异步结果：** 读取和订阅按需要区分加载、失败、成功空数据与非空数据。结果携带足以核对其归属的上下文标识，例如账号或学期；上下文切换时取消旧操作或丢弃迟到结果。供异步外部写入的快照还需有可比较的版本或等效顺序标识。
- **外部输出：** 对会覆盖目标现有数据的操作，只有来源匹配且已就绪的结果才能用于替换；加载或失败不能被当作成功空数据。成功空数据如何处理，由目标的写入规则定义。同一目标的并发写入按版本或等效顺序协调。需要持续同步的目标在失败后保留待同步状态，重试以最新结果为准且不得产生重复副作用。提醒、系统日历和原生 Widget 按各自的写入规则应用这些要求。
- **账号边界：** v2 作为新实现，不编写历史数据迁移代码。账号切换时隔离旧账号的任务、缓存和外部结果；退出时按数据保留策略清理，清理中断后能继续，不能让旧任务写回。
- **基础设施生命周期：** 共享连接等设施由启动装配创建、注入并关闭；通用连接能力可以放在 `core`。功能的用例或 store 使用注入的设施；功能专属的表、映射和读写规则仍归该功能所有，`core` 不反向导入功能代码。
